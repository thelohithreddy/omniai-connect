# API Guidelines

> Consistent with docs/MASTER_PROJECT_BIBLE.md. Governs the platform REST API served by
> apps/api. The OpenAPI document generated by FastAPI **is the contract**; `@omniai/types`
> is generated from it once the API stabilizes (see packages/types/src/index.ts).

Version 1.0 · 2026-08-02

---

## 1. Base conventions

- Base path: **`/v1`** (URL major version, §7). All examples below omit the host.
- Resources are **plural, kebab-case** nouns. Canonical resources map 1:1 to the domain
  model (Bible §4):

| Resource path | Domain term |
|---|---|
| `/v1/workspaces` | Workspace |
| `/v1/connectors` | Connector |
| `/v1/connections` | Connection |
| `/v1/tools` | Tool |
| `/v1/tool-calls` | Tool Call |
| `/v1/members` | Member (a user's membership in a Workspace, with a role) |
| `/v1/api-tokens` | Workspace-scoped API token (machine identity, ADR-0002) |

- Nesting is shallow: at most one level (`/v1/connections/{id}/tools`); deeper
  relationships are expressed with filters (`/v1/tool-calls?connection_id=…`).
- JSON everywhere; `snake_case` field names (matching Pydantic schemas); timestamps are
  RFC 3339 UTC (`2026-08-02T12:00:00Z`); IDs are opaque strings — clients never parse
  them.
- Every response carries `X-Request-Id`; the same value appears in structured logs and in
  error bodies (Bible §6.6).

- **Human workspace selection: `X-Workspace-Id: <uuid>`** (ADR-0016). A human (Better Auth
  JWT) that belongs to more than one Workspace names its target with this header; it is a
  *selection*, verified against membership server-side, never authorization. Required when
  the caller has multiple memberships; optional (auto-bound) when they have exactly one. A
  value naming a Workspace the caller is not a member of — or a duplicate/malformed header —
  fails as the uniform 401, with no disclosure of whether that Workspace exists. Machine API
  tokens ignore it: their Workspace is the token's. It is the single selection mechanism — a
  `workspace_id` in the path, query, body, or JWT is never authority.

## 2. Methods and status codes

| Method | Use | Success | Notes |
|---|---|---|---|
| GET | Read a resource or list | 200 | Never mutates. Cacheable. |
| POST | Create, or invoke an action | 201 (created) / 200 (action) / 202 (async, §9) | Side-effecting POSTs take idempotency keys (§5) |
| PATCH | Partial update | 200 | Only fields present are changed |
| PUT | Full replace | 200 | Rare; prefer PATCH |
| DELETE | Delete | 204 | Idempotent: deleting a deleted resource is 204 |

Common errors: 400 `validation_error`, 401 `unauthorized`, 403 `forbidden`,
404 `not_found`, 409 (conflicting state), 429 `rate_limited`, 5xx (§6). Cross-tenant
access attempts always return 404, never 403 (SECURITY.md §3).

## 3. Pagination

Cursor-based, on every list endpoint. Offset pagination is forbidden — it breaks under
concurrent writes and invites table scans.

- Request: `?limit=50&cursor=<opaque>`; `limit` defaults to 50, max 100.
- Cursors are **opaque** (encoded internally, signed if they ever carry state). Clients
  must not construct or decode them.
- Response envelope for lists:

```json
{
  "data": [ … ],
  "next_cursor": "b2Zmc2V0OjUw",
  "has_more": true
}
```

`next_cursor` is `null` when `has_more` is `false`. Cursors may expire; an expired
cursor yields `validation_error`.

## 4. Filtering and sorting

- Filters are query parameters named after the field: `?status=active`,
  `?connection_id=conn_123`. Repeated params mean OR within a field
  (`?status=active&status=error`).
- Time-range filters use `_after`/`_before` suffixes: `?created_after=2026-08-01T00:00:00Z`.
- Sorting: `?sort=-created_at` (leading `-` for descending). Each endpoint documents its
  sortable fields; default is `-created_at`. Unknown filter/sort fields are a
  `validation_error`, not silently ignored.

## 5. Idempotency

Any POST that creates side effects (creating Connections, executing Tool Calls, issuing
api-tokens) accepts an **`Idempotency-Key`** header (client-generated UUID):

- First request: processed normally; the response is stored against the key (Redis,
  24 h TTL) scoped to the Workspace.
- Retry with the same key + same body: stored response replayed.
- Same key + different body: 409 with code `validation_error`.

Retries are safe by construction; SDK adapters set the key automatically.

> **Exception — credential-issuing endpoints.** `POST /v1/api-tokens` does not accept
> `Idempotency-Key`. Replaying a stored response means storing a plaintext bearer token in
> Redis for 24 hours, which contradicts the "shown exactly once" guarantee in SECURITY.md
> §4.3. Retrying without a key issues a second token, which is safe and revocable. See
> ADR-0010; this section needs amending to either exempt such endpoints or store a
> key → resource-id marker instead of the response body.

## 6. Error envelope

Exactly the `ApiError` shape in `packages/types/src/index.ts` — no other error format
ever leaves the API:

```json
{
  "error": {
    "code": "connector_error",
    "message": "Upstream returned 503 for tool 'crm.create_contact'.",
    "details": { "tool": "crm.create_contact", "upstream_status": 503 },
    "request_id": "req_01J4X8…"
  }
}
```

- `code` is machine-readable and stable (taxonomy below); `message` is human-readable and
  may change wording; `details` is optional structured context; `request_id` always
  matches `X-Request-Id`.
- Services raise domain exceptions; one handler layer maps them to this envelope
  (CODING_STANDARDS.md §2.4).

### 6.1 Error-code taxonomy

| Code | HTTP | Meaning |
|---|---|---|
| `validation_error` | 400 / 409 / 422 | Malformed request, bad params, expired cursor, idempotency body mismatch. `details` includes field errors. |
| `unauthorized` | 401 | Missing/invalid session token or API token. |
| `forbidden` | 403 | Authenticated, but role lacks the capability (SECURITY.md §4.1). |
| `not_found` | 404 | Resource absent — or outside the caller's Workspace. |
| `rate_limited` | 429 | Rate limit or quota exceeded. `Retry-After` header set. |
| `connector_error` | 502 | The upstream API returned an error the runtime couldn't normalize into a Tool result. |
| `upstream_timeout` | 504 | The upstream exceeded the runtime timeout (default 30 s, Architecture §7). |
| `internal` | 500 | Our bug. Reported to Sentry with `request_id`; message is generic, never a stack trace. |

New codes require an entry in this table (same PR) and a CHANGELOG note. Codes are
additive within v1 — clients must tolerate unknown codes.

## 7. Rate-limit headers

Every authenticated response includes:

| Header | Meaning |
|---|---|
| `X-RateLimit-Limit` | Requests allowed in the current window |
| `X-RateLimit-Remaining` | Requests left in the window |
| `X-RateLimit-Reset` | Unix timestamp when the window resets |

429 responses additionally set `Retry-After` (seconds). Limits are enforced per
Workspace and per API token in Redis (Architecture §3.2); Tool Call quotas are a
separate, billing-relevant layer that fails closed (Architecture §7).

## 8. Versioning and deprecation

- **Major version in the URL** (`/v1`). A new major version is a last resort and needs
  an ADR.
- **Within v1, changes are additive only:** new endpoints, new optional fields, new
  enum values, new error codes. Never remove/rename fields, change types, or tighten
  validation on existing inputs.
- Deprecation policy: deprecated endpoints/fields are announced in CHANGELOG.md, marked
  in OpenAPI, and served for **at least 6 months** with a `Sunset` header (RFC 8594)
  carrying the removal date and a `Deprecation` header. Removal only at a major version.

## 9. Async operations

Long-running work (spec ingestion, slow Tool Calls — Architecture §6) uses one contract:

1. POST returns **202 Accepted** with an operation resource:
   `{"id": "op_…", "status": "pending", "resource_url": null}`.
2. Client polls `GET /v1/operations/{id}` — status transitions
   `pending → running → succeeded | failed`; `succeeded` includes `resource_url`,
   `failed` includes an `error` object using the §6 envelope's inner shape.
3. Poll with backoff; operations are retained for 24 h. Webhooks (§10) can replace
   polling when configured.

## 10. Webhooks

- Deliveries are POSTs with a JSON body `{id, type, created_at, data}` and are signed:
  `X-OmniAI-Signature: t=<unix_ts>,v1=<hex HMAC-SHA256 of "<t>.<raw body>">` using the
  endpoint's secret (shown once at creation, per SECURITY.md secret rules). Receivers
  must verify the signature and reject timestamps older than 5 minutes (replay
  protection).
- Retry policy: exponential backoff with jitter over ~24 h (e.g. 1 m, 5 m, 30 m, 2 h,
  6 h, 24 h); a 2xx stops retries; endpoints failing for 3 days are auto-disabled and
  the Workspace notified.
- Deliveries may arrive out of order and more than once — handlers must be idempotent
  (use the event `id`).

## 11. OpenAPI as the contract

FastAPI generates the OpenAPI document from the Pydantic schemas (schema-first, Bible
§6.5). That document is the single API contract: docs render from it, `@omniai/types`
will be generated from it, and contract tests validate responses against it. If the spec
and behavior disagree, it's a bug in whichever changed last — fix in the same PR.
